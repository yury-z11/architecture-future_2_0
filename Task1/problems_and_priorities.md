# Task 1 — Проблемные места и приоритизация

## Контекст

Компания «Будущее 2.0»: медицинский холдинг + банк + ИИ-сервисы.
Текущий стек: DWH на MS SQL Server 2008, PowerBuilder, Power BI, ESB (Apache Camel), ИИ на Python, Финтех на Go/Java.

---

## 1. Выявленные проблемные места

| # | Проблема | Описание | Затронутые бизнес-сценарии |
|---|----------|----------|--------------------------|
| P1 | **Монолитный DWH (SQL Server 2008)** | Вся бизнес-логика сосредоточена в одной БД. End-of-life платформа без поддержки. Любые изменения требуют согласования и затрагивают все направления | Отчётность, финтех-интеграция, ИИ-аналитика, масштабирование |
| P2 | **Производительность отчётности** | Сложные запросы занимают часы из-за объёма данных (сотни ТБ) и большого числа трансформаций | Управленческие решения, операционная отчётность, SLA клиентам |
| P3 | **Отсутствие domain-изоляции** | Финтех, клиники и ИИ-сервисы работают через единый DWH. Любое изменение в одной части влияет на другие | Независимое развитие направлений, time-to-market, устойчивость |
| P4 | **Устаревший интерфейс (PowerBuilder)** | Клиентский интерфейс для операторов клиник на снятой с поддержки технологии. Сложно развивать и поддерживать | Операционная работа клиник, онбординг сотрудников |
| P5 | **ESB Apache Camel как единая точка отказа** | Все интеграции проходят через одну шину. Нет гибкости для добавления новых бизнес-направлений без изменения шины | Интеграция новых партнёров (фармацевтика, электроника), надёжность |
| P6 | **Отсутствие Self-Service BI** | Нет портала самообслуживания. Сотрудники зависят от ИТ при формировании любого отчёта | Скорость принятия решений, автономность бизнес-пользователей |
| P7 | **Смешение медицинских и бизнес-данных** | Медицинские карты, финансы и операционные данные хранятся в единой схеме без чёткого разграничения доступа | Соответствие регуляторным требованиям (GDPR, ФЗ-152, медицинская тайна) |
| P8 | **Отсутствие облачной инфраструктуры** | Вся инфраструктура on-premise. Сложно масштабировать при росте нагрузки и подключении новых направлений | Масштабирование, disaster recovery, гибкость ресурсов |

## 2. Приоритизация по MoSCoW

### Must Have (критично, блокирует бизнес)
- **P1** — Замена монолитного DWH: без этого невозможно независимое развитие направлений
- **P3** — Domain-изоляция: напрямую связана с целью бизнеса — развивать каждое направление отдельно
- **P7** — Разграничение доступа к данным: регуляторный риск (штрафы, отзыв лицензий)

### Should Have (важно, решается в первую очередь после Must)
- **P2** — Производительность отчётности: прямое влияние на скорость управленческих решений
- **P6** — Self-Service BI: ключевая цель бизнеса — портал самообслуживания
- **P5** — Замена ESB: необходимо для подключения новых партнёров без регрессий

### Could Have (улучшает, но не блокирует)
- **P8** — Облачная инфраструктура: ускоряет решение P1, P2, P5, но сам по себе не блокирующий
- **P4** — Замена PowerBuilder: болезненно, но не критично прямо сейчас

### Won't Have (откладываем)
- Полная замена всех legacy-систем одновременно
