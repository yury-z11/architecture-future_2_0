# Task 2 — Разделение на домены и потоки данных

## 1. Определение доменов

Основа разделения — Domain-Driven Design (DDD): каждый домен отвечает за свой bounded context, имеет собственные данные и не разделяет схему БД с другими.

### Домен 1: Головной офис (Analytics Domain)
**Ответственность:** консолидированная отчётность, KPI, финансовая отчётность, управление доступом к данным.

**Данные:** агрегированные показатели из всех доменов. Медицинские карты и истории болезней — **исключены**.

**Ключевые компоненты:**
- Data Platform (Data Lakehouse)
- Self-Service BI портал
- Data Catalog

**Почему отдельный домен:** Нужна единая точка консолидации без необходимости читать оперативные данные из каждой системы напрямую. При добавлении нового направления (фармацевтика, электроника) — просто подключается новый продюсер событий.

---

### Домен 2: Клиники (Medical Operations Domain)
**Ответственность:** работа с пациентами, расписания, инвентаризация, персонал.

**Данные:** данные клиентов (не медкарты), инвентарь, расписание, персонал.

**Исключено из домена:** медицинские карты, истории болезней, результаты диагностики — хранятся в изолированной системе EHR с отдельным доступом.

**Почему отдельный домен:** Клиники имеют собственный операционный ритм. Отделение от финтех позволяет клиникам масштабироваться и обновляться независимо. Обеспечивает соответствие медицинским регуляторам.

---

### Домен 3: Финтех (Financial Services Domain)
**Ответственность:** счета, кредиты, платежи, банковские операции.

**Данные:** финансовая история, счета, кредиты, транзакции.

**Почему отдельный домен:** Наличие банковской лицензии требует строгой изоляции финансовых данных. Разные регуляторные требования (ЦБ РФ, PCI DSS). Независимые команды с отдельным роадмапом.

---

### Домен 4: ИИ-сервисы (AI Domain)
**Ответственность:** ИИ-анализ медицинских данных, ML-модели.

**Данные:** только читает медицинские данные из EHR по защищённому каналу. Не производит данные для общей витрины.

**Почему отдельный домен:** Специфический стек (Python, GPU), особые требования к данным, отдельный цикл релизов.

---

### Домен 5: Партнёры (Partner Integration Domain)
**Ответственность:** будущие интеграции — фармацевтика, производитель медоборудования.

**Данные:** каталоги, заказы, поставки.

**Почему отдельный домен:** Партнёры — внешние организации с собственными системами. Изоляция через API Gateway защищает внутренние данные. Подключение нового партнёра не затрагивает другие домены.

---

## 2. Логика разделения и преимущества для бизнеса

| Преимущество | Описание |
|---|---|
| **Ускорение time-to-market** | Каждая команда деплоит независимо. Финтех может выпускать новые продукты, не ожидая клиники |
| **Снижение зависимости от DWH** | Домены не читают напрямую из монолита. Данные передаются через события (Kafka) |
| **Независимое масштабирование** | В высокий сезон клиники можно масштабировать только медицинский домен |
| **Regulatory compliance** | Медицинские данные изолированы. Финансовые данные отделены согласно требованиям ЦБ |
| **Подключение новых бизнесов** | Фармацевтика, электроника — подключаются как новые продюсеры событий без изменения существующих доменов |
| **Fault isolation** | Сбой в финтех-домене не останавливает операции клиник |

## 3. Data Flow Diagram (DFD) — описание потоков

### Основные потоки данных:

**Поток 1: Операционные события → Data Platform**
```
Клиники → [Kafka: clinic.events] → Data Platform → Self-Service BI
Финтех  → [Kafka: fintech.events] → Data Platform → Self-Service BI
```

**Поток 2: ИИ-анализ**
```
EHR (медкарты) → [Защищённый канал] → ИИ-сервис → ML модели
ИИ-сервис → [Kafka: ai.results] → Data Platform (только агрегаты без ПД)
```

**Поток 3: Внешние партнёры**
```
Фармацевтика → [API Gateway] → Partner Domain → [Kafka] → Data Platform
Медоборудование → [API Gateway] → Partner Domain → Clinic Domain
```

**Поток 4: Self-Service BI**
```
Сотрудник → Self-Service Portal → Data Platform (RBAC) → Отчёт
```

**Поток 5: Финтех-клиент**
```
Клиент → API Gateway → Fintech API → Fintech DB
Fintech API → [Kafka: payment.events] → Data Platform (агрегаты)
```

### Что НЕ передаётся в Data Platform:
- Медицинские карты пациентов
- Детали диагностических исследований
- Биометрические данные
